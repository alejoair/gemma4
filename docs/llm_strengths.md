# What LLMs do well and badly: evidence for the step.py interface (2026-10-09)

Evidence strength: **C** = controlled study or ablation, **B** = benchmark or leaderboard, **V** = vendor guidance, **A** = anecdote or practitioner report.
"Verified" means I read the number on the source page (abstract or HTML), not in a summary.
Current design checked: `agent/prompts/swe.md`, `configs/sampling.yaml`, `_args.py`, `_edit.py` (commit 8c95d1d).

## 1. Edit formats

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 1.1 | Rewriting whole functions ("high level" hunks) beats surgical line edits. Prompts without it gave **30–50% more editing errors**. Aider says "GPT is terrible at working with source code line numbers". Flexible application (relative indentation, varied context) matters: turning it off gave **9× more editing errors**. Aider also reports that GPT "outdents all of the code", so it re-indents edits. | [aider udiff](https://aider.chat/docs/unified-diffs.html) (verified) | C (internal benchmark, GPT-4 Turbo) | Whole-definition edits and `_reindent`: **already done**. Gap: edits outside a function still ask for **first and last line numbers** (see 1.3). |
| 1.2 | Format compliance falls for ~32B open models with diffs. Qwen2.5-Coder-32B: **whole 16.4%** correct with 99.6% well-formed edits, vs **diff 8.0%** with 71.6% well-formed. QwQ-32B diff: 67.6% well-formed; Qwen3-32B diff: 83.6%. gemma-3-27b whole: 100% well-formed (4.9% correct). | [aider leaderboard](https://aider.chat/docs/leaderboards/) | B | Supports whole-definition rewrite for a 31B model: **already done**. |
| 1.3 | Models are "notoriously bad at counting line numbers" (a line number is often a single token chosen in one step). Diffs are out of distribution: models have seen far more full files. Cursor found most models produced inaccurate search/replace diffs; only Claude Opus was reliable. They rewrite whole files of ≤400 lines. | [Cursor instant apply](https://cursor.com/blog/instant-apply) | A/V (vendor engineering) | **Change:** for module-level edits, drop `first, last` line numbers. Anchor the edit by name instead: the assigned name, the import, or the `if __name__` block. Or use an old-text/new-text pair matched whitespace-insensitively. Keep line numbers in the view (reading them is fine); only stop asking the model to *produce* them. |
| 1.4 | Formats that index edits by line number do far worse than full rewrites, even when the input is numbered. Structure-aware units (function or block) match full-rewrite accuracy at about 30% lower cost. | [To Diff or Not to Diff, arXiv 2604.27296](https://arxiv.org/abs/2604.27296) (abstract verified; the line-number claim is from a search summary, not verified) | C | Same as 1.3. |
| 1.5 | Diff-XYZ: search/replace is best for *large* models generating diffs. "Smaller open models benefit little from any formatting choice." | [arXiv 2510.12487](https://arxiv.org/abs/2510.12487) (abstract verified) | B | For a 31B model the main gain is in **not making it count or quote exactly**, not in the choice of diff dialect. |
| 1.6 | SWE-Edit splits the work: a viewer and an editor with a clean context give **+2.1 pp** on SWE-bench Verified and **−17.9%** cost. A Qwen3-8B editor trained to choose find-replace or whole rewrite gained **+12.5 pp** edit success. | [arXiv 2604.26102](https://arxiv.org/abs/2604.26102) (verified) | C | Option: write each place in an `agent_tool` editor with a fresh session, seeing only the edit window. This is the "clean context" idea; it costs turns. |
| 1.7 | Code is worse when wrapped in JSON than in markdown fences, for all 4 models tested (gpt-4o-05: −0.4, within noise). It also gives more `SyntaxError` and `IndentationError`, and strict mode did not help. | [aider code-in-JSON](https://aider.chat/2024/08/14/code-in-json.html) (verified) | C | Gemma's `<|"|>` delimiter avoids quote escaping, so the risk is lower. `_unescape` handles stray `\"`: **already done**. If 31B traces show `\n` or `\"` escaping inside code args, unescape those too. |

## 2. Selection vs generation; lists and position

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 2.1 | The bias in multiple-choice answers is mostly **token bias on the option ids** (A/B/C), across 20 LLMs, more than position bias. | [Zheng et al., ICLR 2024](https://arxiv.org/abs/2309.03882) | C | Names instead of C2/P1: **done** (8c95d1d). Never reintroduce letter or number ids. |
| 2.2 | Lost in the middle (GPT-3.5, 20 documents): answer first **75.8%**, middle **53.8%** (below closed-book **56.1%**), last **63.2%**. Putting the query **before and after** the data brought key-value retrieval to near-perfect. | [Liu et al.](https://arxiv.org/html/2307.03172) (verified, Table 6) | C | **Change:** in each script answer, put the decision question and the requirements *last*, right before NEXT, as well as first. Keep the candidate list short (≤10, already done). |
| 2.3 | Smaller models are more order-sensitive. Permutation self-consistency improved ranking by **+157%** for LLaMA2-7B, +28% for 13B and +12% for 70B (relative). | [Tang et al., NAACL 2024](https://arxiv.org/html/2310.07712v2) (verified) | C | Order the list by our rank with the best first (first slots are read). Do not shuffle; we cannot afford repeated calls. |
| 2.4 | Agents never asked for a second page: **0** agent-initiated requests for chunk 2. Whether the gold item is in the first chunk mattered more than its rank in it. | [Agents Don't Paginate, arXiv 2608.26130](https://arxiv.org/abs/2608.26130) (verified) | B | Whatever the 10,000-character cap cuts is lost. Put everything needed first. No "ask for more" paths: **already done** (no questions). |
| 2.5 | Classification-like outputs *improve* under format constraints (DDXPlus with Gemma 2 9B: 22.9 → 53.0 with JSON). Reasoning tasks degrade (GSM8K with LLaMA3-8B: 74.7 → 48.9), partly because "100%" of GPT-3.5 JSON answers put the answer key before the reason. | [Let Me Speak Freely](https://arxiv.org/html/2408.02442v1) (verified) | C | The choose step is classification, so a constrained choice from names is right. The edit step is generation: reasoning must come *before* the args, in the thinking channel. That is **already done** ("Think before the call"), but see 6.3 on the budget. |

## 3. Copying fidelity

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 3.1 | Exact transcription of long or high-entropy strings fails. The per-token error compounds with length, and instruction tuning pushes models to summarize. | [arXiv 2601.03640](https://arxiv.org/abs/2601.03640) (no numbers in abstract) | C (claim only) | **Risk:** step 1 asks the model to copy the statement verbatim (up to 3,000 characters, about 800 output tokens) as `args[0]`. If the script only needs it for terms and requirements, accept any near-copy. Better, find the statement in the sandbox or derive it from `{problem_description}` some other way. Never refuse an inexact copy. |
| 3.2 | Anthropic: resolving UUIDs to "semantically meaningful and interpretable language (or even a 0-indexed ID scheme)" reduces hallucinations in retrieval tasks. Prefer `name` over `uuid`; use `user_id` rather than `user` as a parameter name. | [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (verified quote) | V | **Done** for names. Corollary: accept every reasonable spelling of a name (`Session.send`, `send`, `requests.sessions.Session.send`, `def send`). Resolve it by unique suffix match instead of refusing. |
| 3.3 | Anthropic's SWE-bench work: the model made path errors after leaving the repository root. Requiring absolute paths fixed it ("used this method flawlessly"). The rule is poka-yoke: change the arguments so mistakes are harder. | [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (verified) | V/A | Already followed: the script resolves places. Apply the same idea to every argument the model has to type. |

## 4. Formats seen in training

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 4.1 | "Keep the format close to what the model has seen naturally occurring in text on the internet". Avoid formats that require counting thousands of lines or escaping code in JSON. | [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | V | The `  79|code` view looks like `cat -n` (familiar). Show test failures as pytest's own short `E   assert …` lines and the traceback tail, not paraphrased. |
| 4.2 | Anthropic: the response structure (XML, JSON or Markdown) matters, and "there is no one-size-fits-all"; evaluate it. Return only high-signal information. Truncate with guidance. | same as 3.2 | V | Already done (capped answers). |
| 4.3 | YAML is worse than JSON for tool calls (syntax and structure accuracy), partly because of indentation sensitivity. | [CallNavi, arXiv 2501.05255](https://arxiv.org/pdf/2501.05255) (via summary; not verified) | B | Irrelevant to us: args are a list of strings. |
| 4.4 | SWE-agent ACI on Lite: 18.0% vs **11.0%** for a shell-only agent. No edit command: 10.3. Iterative search: 12.0 (summarized search: 18.0). Full-file view: 12.7; 30-line window: 14.3. Full history: 15.0 (last-5 observations: 18.0). Failed edits: after one, success falls from 90.5% to 57.2%. | [SWE-agent](https://arxiv.org/html/2405.15793) (verified) | C | Mostly already applied. The 90.5 → 57.2 drop is the reason to make edits hard to fail (1.3, 3.2). |
| 4.5 | CodeAct (Python as the action) is up to +20% over JSON or text actions. Gains grow with model capability and are small on simple tasks. | [CodeAct](https://arxiv.org/html/2402.01030v4) | C | Not available (no Python tools). Not pursued. |

## 5. Small-model failure modes in loops

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 5.1 | **A failed call in the context makes models repeat it.** P(repeat the failed call) went from **0.06 to 0.54**, with **19%** token-for-token copies under greedy decoding. The surface form of the failed call explains **83%** of the effect. Replacing the verbatim failed call with a runtime description removed **76%** of it. "Do not repeat" instructions did **not** help, and retrying from a clean context was the worst setup. Models were 135M–1.7B, so the effect on 31B is untested. | [Feedback That Backfires, arXiv 2608.23651](https://arxiv.org/abs/2608.23651) (verified) | C | **Change:** refusal and error answers should never echo the model's bad args or code. Describe the failure in one line, then give a *different*, fully filled concrete call to make next. Drop any prompt text like "don't repeat". |
| 5.2 | Self-conditioning: models "become more likely to make mistakes when the context contains their errors from prior turns". Scaling does not fix it, but thinking mitigates it. | [Illusion of Diminishing Returns, arXiv 2509.09677](https://arxiv.org/abs/2509.09677) (verified quotes; no numbers in abstract) | C | Same as 5.1. Also keep thinking on (done). After an undone edit, the next window should show the current code fresh, not a diff of the failed attempt. |
| 5.3 | Reasoning amplifies tool hallucination. Even switching to step-by-step thinking at inference raised the calls to non-existent tools, and mitigations cost utility. | [Reasoning Trap, arXiv 2510.22977](https://arxiv.org/abs/2510.22977) (verified) | C | Thinking is needed, so make hallucinated calls harmless (5.4). |
| 5.4 | A closed-world resolver (registry membership plus a signature check) catches fabricated calls. Fabricated calls concentrate on the unconstrained raw-JSON surface (**34 vs 3**), and scale does not help (675B ≈ 7–8B). | [arXiv 2609.19425](https://arxiv.org/abs/2609.19425) (verified; single-author preprint) | C (weak) | **Change (poka-yoke):** we saw calls to `show.py`, `grep.py`, `nonexistent.py` (V1, V5, V6). Add tiny forwarding stubs `scripts/show.py`, `edit.py`, `locate.py`, `grep.py`, `search.py`. Each one runs `step.py`'s logic or answers "use scripts/step.py: NEXT …". In step.py, accept a decision even when the args arrive in a different but recognizable shape. |
| 5.5 | Gemma 4 in agents (ADK via Ollama, OpenCode, LM Studio) looped on tool calls. Advice: cap retries, suppress duplicate calls, never feed malformed tool-call turns back into history. | [HF forum on Gemma 4 issues](https://discuss.huggingface.co/t/gemma-4-bug-fixes-and-research-request/176979) | A | Duplicate suppression is in the journal (already done). Malformed turns can't be removed from ADK history, so use 5.1 instead. |
| 5.6 | Weak models loop: Qwen3-VL-8B averaged 16.6 tool calls for 23.4% accuracy, vs GPT-5 with 3.4 calls for 41.3%. | [SciAgentGym, arXiv 2602.12984](https://arxiv.org/pdf/2602.12984) (via search summary) | B | Budget caps are already done. |
| 5.7 | Instruction density: models favour earlier instructions (primacy bias). Adherence decays as the number of instructions grows. | [IFScale, arXiv 2507.11538](https://arxiv.org/abs/2507.11538) (summary) | B | Keep `swe.md` short, with the most important rule first. The prompt is about 30 lines (already done). |

## 6. Gemma 4 specifics

| # | Claim | Source | Str. | Our design |
|---|---|---|---|---|
| 6.1 | Tool calls are `<|tool_call>call:name{key:<|"|>str<|"|>,n:42}<tool_call|>`. Keys are unquoted, and **every string value** is wrapped in the single `<|"|>` token, which protects braces, commas and quotes inside it. Responses are `<|tool_response>response:name{…}<tool_response|>`. | [Gemma 4 prompt formatting](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4) | V | The prompt already shows this form. Check that vLLM tokenizes the literal `<|tool_call>` text in our *instruction* as text and not as the special tokens. If it does not, the model sees fake control tokens in the system turn. |
| 6.2 | Sampling: "temperature=1.0, top_p=0.95, top_k=64 **across all use cases**". | [HF model card gemma-4-31B-it](https://huggingface.co/google/gemma-4-31B-it) (verified) | V | **Change to test:** we use temperature 0.2 with no top_k. Qwen3's card warns that greedy-like decoding in thinking mode causes "endless repetitions" ([Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B)). That is an analogy, not Gemma evidence. A/B test 1.0/0.95/64 (or 0.6) against 0.2 on loops and malformed calls. |
| 6.3 | Thinking: keep thoughts between function calls in the same turn, and strip them between user turns. Thinking "improves tool-selection and parameter accuracy" (Google's example allows 1,024 new tokens with thinking vs 128 without). The 31B may emit a thought channel even with thinking off. A "LOW" thinking system instruction cut thinking about 20%. | [prompt formatting](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4), [function calling](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4) | V | `include_thoughts: true`: **done**. A `thinking_budget` of 512 is shared by all steps; the edit step writes whole functions after reasoning. Consider 1,024 if the timing allows. |
| 6.4 | vLLM: use `--tool-call-parser gemma4 --reasoning-parser gemma4` with the gemma4 chat template. Streaming parsing had bugs: raw `<|"|>` leaked (#44522), decimals were corrupted (#39380), and there were quote and truncation issues (#39069). The non-strict fallback regex stops at the first `}`, so a brace inside a value can truncate args. | [vLLM recipe](https://recipes.vllm.ai/Google/gemma-4-31B-it), [gemma4_utils](https://docs.vllm.ai/en/latest/api/vllm/tool_parsers/gemma4_utils/), [#44522](https://github.com/vllm-project/vllm/issues/44522) | V/A | The harness is fixed, but `_args.py` repair should expect `<|"|>` / `"|>` fragments, and code args cut at a `}`. Our own repair layer already handles part of this. |

## 7. Vendor tool-design guidance

- **Consolidate tools around tasks.** Use `schedule_event` instead of list plus create. One `step.py` is this: **done**. ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents))
- **Errors that steer.** Give specific, actionable guidance, not codes or tracebacks. Combine it with 5.1: describe, then give the next concrete call.
- **Describe as to a new hire; the "intern test".** Could a person use the tool from only what the model sees? The OpenAI intern-test wording comes from a third-party copy; not verified on openai.com.
- **Enums and strict schemas** make invalid values unrepresentable. The ADK cannot constrain `args`, so the script must resolve fuzzy input (3.2).

## 8. Other "obvious once said" items

1. **The model reads the first and last parts of a long answer.** Lay out each window as: current question → code → context → question again → NEXT (2.2, 2.4).
2. **Don't ask the model to produce what the script already knows.** That covers line numbers, file paths, the copied statement and place names that were already chosen. Every typed token is a chance to fail (3.1, 1.3).
3. **Selection is easier than generation, but only within the candidate list.** BLAgent's LLM reranking was *worse* than its dense retriever (Top-10 82.3 vs 87.3), and the LLM often returned fewer items than asked ([arXiv 2605.17965](https://arxiv.org/pdf/2605.17965), via summary). Always allow "none of these" plus free names (already done), and accept fewer picks than asked.
4. **The failed attempt is an example.** Whatever stays in history is imitated (5.1, 5.2). Successful example calls (the NEXT line) should be the most recent thing the model sees.
5. **Model size does not fix fabricated tools, self-conditioning or format errors in small models** (5.2, 5.4, 1.5). Fix them in the interface.
