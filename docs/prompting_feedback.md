# How to give feedback to an LLM agent so that it corrects itself (2026-10-09)

Scope: verdicts, refusals, the repeat guard and the coverage map of `agent/skills/fix-issue/scripts/step.py` and `_tests.py`.
This report does not repeat `docs/llm_strengths.md` (Feedback That Backfires, self-conditioning, Reasoning Trap, the
Anthropic "errors that steer" line) or `docs/audit_v10.md` (#3 repeat guard, #4 false OK, #7 coverage by words,
#13 BROKEN excerpt). Where a finding supports an audit fix, it says so and adds only the new evidence.
Evidence strength: **C** controlled study or ablation, **B** benchmark, **V** vendor guidance, **P** practitioner
blog or docs. Every number below was checked in the paper's text or tables unless it is marked "abstract only".

## 1. Error and refusal design

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 1.1 | A rejected edit should say plainly that it was **not applied**, name the error and show where it is. SWE-agent shows "Your proposed edit has introduced new syntax error(s)", the error, the edit as it would have looked, the original, and "Your changes have NOT been applied". Linting is worth **+3.0** (18.0 vs 15.0 on Lite). After a good edit the viewer is centred on the edited lines, and an empty output gets "Your command ran successfully and did not produce any output". | [SWE-agent](https://arxiv.org/html/2405.15793) | C | "NOT APPLIED … nothing was changed": **done**. **Gap:** the compile error gives a *file* line number, which the model cannot use (B1). Show the one offending line of the new code with its error ("this line of your new code: `…` → unexpected indent"). Quote that line only, not the whole attempt (see 4.1). |
| 1.2 | Errors should "communicate specific and actionable improvements" instead of "opaque error codes or tracebacks". If invalid-parameter errors are frequent, the **descriptions or examples** need fixing, not just the error text. Truncated output should steer. | [Anthropic, Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) | V | The second point matters for the ADK error we cannot change: put the fix into the prompt (4.3). |
| 1.3 | With 6 models and 1,694 fault trials, loud errors were noticed **91.3%** of the time and silent wrong values **58.8%**. A **missing tool** had the worst recovery (**39.9%**, against about 60% for the other faults). **26.8%** of agents reported a problem when the call had succeeded. One prompt line, "check each result", changed nothing (+0.6 and +2.5, n.s.). Same-tool runs of 3+ appeared in 12.5–22.2% of fault trials. | [Loud Failures, Quiet Failures, arXiv 2610.10062](https://arxiv.org/html/2610.10062v1) | C (preprint) | (a) `Skill '「swe」' not found` is the missing-tool case, the one with the worst recovery. (b) Make success unmistakable: "APPLIED, NOT VERIFIED" can read as a failure, so start the line with what happened to the code (`KEPT`). (c) Do not add "check the output" lines to the prompt. |

## 2. What form of execution feedback helps

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 2.1 | A **failing unit test with expected vs. actual** is the best format, and explanations and traces add little. GPT-4 on TransCoder: base 77.3, Simple 80.9, UT **88.8**, +Expl 90.4, +Trace 89.5. GPT-4 on MBPP: 72.8, 78.8, **80.6**, 80.4, 80.2. Traces can hurt: Codex on TransCoder scores 87.9 with traces vs 91.6 with UT. Without execution, Codex Simple on MBPP **fell** to 57.6 from 61.4, and the models were "overconfident in their own initial predictions". StarCoder 15.5B gained less: 47.2 → 53.2. | [Self-Debugging, ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/file/2460396f2d0d421885997dd1612ac56b-Paper-Conference.pdf), Tables 2–3 | C | BROKEN shows FAILED lines plus the last 25 traceback lines, cut from the end at 1,500 characters. **Change** (this extends audit #13): lead with the test name, the call it makes, and pytest's `E` lines (expected vs actual). Drop the frames. The 25-line tail is the "+Trace" variant, which adds nothing over UT. |
| 2.2 | Average Repair@1 by feedback type over 5 LLMs: test **61.0**, minimal "the code is wrong" 56.9, compiler 55.8, and human-style verbal feedback **50.5**, the worst ("over-complicated or misinterpreted solutions"). Gains plateau after 2–3 rounds. Removing docstrings or context cost the most (52.6 → 47.4). CoT changed nothing, and few-shot cost 2.1. | [FeedbackEval, arXiv 2504.06939](https://arxiv.org/html/2504.06939v1) | B | Our own prose ("Read the failing test: send a corrected edit … that keeps it passing") is verbal feedback, so keep it to one line. Keep what the change must do in every window: **done** (the requirements are repeated). |
| 2.3 | In 0.5–1.5B models, what helps is a falsifying **fact**, not the wording. Code plus facts against bare code: 21 vs 3 unlocks. Against a generic-bullet placebo: **+15**. Instructions alone: +3 (n.s.). Blind resampling tied the best feedback (26 vs 26). | [Falsification, Not Exposure, arXiv 2606.31511](https://arxiv.org/abs/2606.31511) | C (abstract only; tiny models) | Instruction text in refusals is close to worthless. A concrete counterexample is what counts. |
| 2.4 | Adding execution traces helped in only **2 of 6** configurations, and the benefit fell as the traces got more complex (abstract only). LDB's per-block runtime values: up to **+9.8%** (abstract). | [arXiv 2505.04441](https://arxiv.org/abs/2505.04441), [LDB](https://arxiv.org/abs/2402.16906) | C | Do not add traces. At most, one actual value next to the expected one. |
| 2.5 | Retries decay fast. Two rounds capture **76–95%** of the achievable gain. Assertion errors are the hardest (~45% repaired vs ~77% for name errors). Debugging Decay: 60–80% of the effect is lost within 2–3 attempts (abstract). A fresh start that keeps only the problem statement raised, for example, llama3.1:8b from 72.6 to 82.3, but 2 of 8 models got worse. Olausson: diversity up front beats long repair. GPT-4 on APPS: 10 initial × 1 repair = **1.05×** baseline; 2 × 10 = **0.97×**. | [arXiv 2604.10508](https://arxiv.org/html/2604.10508), [DDI, arXiv 2506.18403](https://arxiv.org/html/2506.18403v2), [Olausson et al., ICLR 2024](https://arxiv.org/abs/2306.09896) | C | `MAX_FAILS = 2`: **done**, and it is consistent with this. After a place is left, the next window must be "fresh": the statement, the requirement and the current code, with no trace of the failed text. The repeat guard must not burn these 2 tries on refused or repeated calls (audit #3). |

## 3. When feedback makes things worse

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 3.1 | **Without new external facts, a request to reconsider lowers accuracy.** GPT-3.5 on CommonSenseQA went from 75.8 to **38.1** after one round of intrinsic self-correction (GSM8K: 75.9 → 75.1). With an oracle that stops at the right answer: 89.7. The review prompt itself "might bias the model to choose another option". | [Huang et al., ICLR 2024](https://arxiv.org/html/2310.01798) | C | The finish view's "NOTHING changed shares its words: **is it covered?**" is exactly such a prompt. It comes from a word match with known false negatives: audit #7 flagged the exact fix in requests s7. **Change:** never ask a question. State the fact and its reliability: "word match only: no change contains the words X, Y". Better, report it only when a real check fails. |
| 3.2 | Challenging a model ("Are you sure?") makes it change its answer **46%** of the time, and accuracy drops **17%** on average. The most effective challenge wording caused about **3×** the damage of the least effective. | [FlipFlop, arXiv 2311.08596](https://arxiv.org/abs/2311.08596) | C | Same as 3.1. "STOP REPEATING", "is it covered?" and "TIME IS UP" are challenges. Use neutral, factual wording. |
| 3.3 | **Inaccurate feedback is the bottleneck.** GPT-4's own feedback was inaccurate in **32/80** cases, against 7/80 for human feedback. Human feedback raised repairs **1.58×** (33.3% → 52.6%). Humans expressed uncertainty in 7/80 cases; GPT-4 in 0/80. Reflexion's self-written tests gave **16.3%** false positives on MBPP (1.4% on HumanEval), and Reflexion scored 77.1 there, below GPT-4's 80.1. LLM verifiers produce false positives, and binary vs detailed feedback made little difference (abstract). | [Olausson](https://arxiv.org/abs/2306.09896), [Reflexion](https://arxiv.org/html/2303.11366), [Valmeekam et al.](https://arxiv.org/abs/2310.08118), [Stechly et al.](https://arxiv.org/abs/2310.12397) | C | A false "OK" costs more than no verdict. Audit #4 proposes "NOT VERIFIED when no selected test executes the changed lines". **Add:** grade the verdict by its evidence and say what was not checked (F3). |
| 3.4 | **Locating the error is the hard part; correction is easy once the model knows where.** GPT-4 finds the first mistake at best **52.87%** of the time. Given the true location, accuracy on the wrong traces rises **+18 to +44** points. A random location gives smaller gains. Backtracking still pays when the locator is 60–70% accurate. | [Tyen et al., arXiv 2311.08516](https://arxiv.org/html/2311.08516) | C | The most valuable part of a verdict is the location: the offending line of the new code, the failing assertion, the requirement with no change. Every negative verdict should name it in words the model can match (F1). |

## 4. Repetition after errors

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 4.1 | **Keep or remove failures? They agree once evidence is separated from surface form.** Manus: "leave the wrong turns in the context … Erasing failure removes evidence". It also says: "The more uniform your context, the more brittle your agent becomes", so it adds structured variation. Reflexion keeps **one** summarized reflection for programming. Laban et al.: restarting with consolidated information beats continuing. DDI: a fresh start keeps only the statement. Feedback That Backfires (known): the verbatim failed call drives repeats. | [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), [Reflexion](https://arxiv.org/html/2303.11366), [Laban et al.](https://arxiv.org/html/2505.06120) | P / C | **Synthesis:** keep the evidence (that it failed, why, and where, in one described line). Drop the surface form (the failed text). Vary the wording. We cannot prune ADK history, so the only lever is the next answer: describe, locate, then give a different, filled NEXT. |
| 4.2 | Near-greedy decoding makes repeats deterministic. When the error text is identical, the next context changes very little, so the same call comes back. Temperature 0 did not fix multi-turn unreliability (still about 30% at 0.0). Practitioner ladders: OpenRouter observes at 2 repeats, blocks at 3, stops at 6, and can escalate. OpenHands flags 4 identical action-observation pairs or 3 action-error pairs. | [Laban et al.](https://arxiv.org/html/2505.06120), [OpenRouter doom-loop](https://openrouter.ai/docs/agent-sdk/call-model/doom-loop-detection), [OpenHands](https://docs.openhands.dev/sdk/guides/agent-stuck-detector) | C / P | Our guard blocks the 2nd identical call within the last 3, which is stricter than the ladders, and it auto-advances in D1 and D2: **done**. **Gaps:** the guard's answer is the same every time and quotes the earlier answer (B5). Make each repeat answer differ (a counter, a different NEXT). Make the 3rd repeat move the work on in **every** step, D4 included. Temperature 0.2 is the analogue of greedy decoding here (B14). |
| 4.3 | The ADK answer `Skill '「swe」' not found.` (checked in `google/adk/tools/skill_toolset.py`) echoes the malformed name, the surface form that drives repeats, and gives no fix. In V10 the model repeated it up to 34 times. | ADK source; 1.2, 1.3 | V / O | **Change:** in `prompts/swe.md`, quote this error text and give the exact fix: "If a call answers `Skill '…' not found`, the name had extra characters. Send skill_name `fix-issue` exactly: no quotes, no brackets." Evidence is weak (vendor guidance plus our traces); measure the number of repeats after it. |

## 5. Positive feedback and progress

| # | Claim and number | Source | Str. | Our design |
|---|---|---|---|---|
| 5.1 | **Recitation of the state helps.** Restating all known information at the end: GPT-4o went from 59.1 (sharded) to **76.6**, and GPT-4o-mini from 50.4 to **66.5**. Restating it every turn: 65.3 and 61.8. Both stay below a single full prompt (93.0 and 86.8). Manus rewrites `todo.md` so that the plan sits at the end of the context. Anthropic keeps a progress file and a feature list that stays "failing" until it has been verified, because the agent "declares victory … too early". | [Laban et al.](https://arxiv.org/html/2505.06120), [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), [Anthropic, long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | C / P / V | Every window already repeats the requirements: **done**. **Add:** one progress line at the top of every answer, built from `git diff` (audit #1): "Kept: Session.send (tests ran it). Now: resolve_redirects (2 of 3). Left: merge_setting. Time 3.1 of 7 min." That covers B10 too. |

## 6. Verdict wording
In short: one binary word (the binary signal carries most of the gain: FeedbackEval simple 56.9 vs test 61.0), then one located fact or expected-vs-actual pair (the detail that helps: 2.1, 3.4), a stated confidence (3.3), and never a false OK (3.3).

## 7. Small and open models
- Self-repair helps only modestly unless the feedback is better than the model's own. Replacing Code Llama's or GPT-3.5's feedback with a stronger model's "beats both the i.i.d. baseline and self-repair at all budgets" (Olausson, C). Self-correction "works well in tasks that can use reliable external feedback" ([Kamoi et al., TACL](https://arxiv.org/abs/2406.01297), survey). Models up to 13B need a strong verifier ([Zhang et al., arXiv 2404.17140](https://arxiv.org/abs/2404.17140), abstract only).
- Gains do not simply shrink with size. Llama 3.1 8B gained +9.8 on HumanEval vs +4.9 for Qwen3 32B, but it repaired only 29.6% of its failures (arXiv 2604.10508).
- **For us:** the 31B does not critique; `step.py` is the external verifier. Its accuracy (no false OK, no false NOTHING) is the main lever, more than its wording.

## Proposed checklist items (for `docs/llm_checklist.md`)

| # | The model does badly / needs | Evidence | Check question |
|---|---|---|---|
| F1 | **Finding where its error is**: it corrects well once told where | Tyen et al.: location +18 to +44 C; SWE-agent linter +3.0 C | Does every negative verdict name where the problem is: the offending line's text, the test name, the requirement? Is it given in words the model can match, never as a file line number? |
| F2 | **Repairing from prose or tracebacks**; it repairs best from a failing test with expected vs actual | Self-Debugging UT ≥ +Expl/+Trace C; FeedbackEval test 61.0 vs verbal 50.5 B; traces help in 2/6 C | Does BROKEN lead with the test name, the call and expected vs actual? Does it say these tests passed before and the code is back? Is it free of traceback frames? |
| F3 | **Doubting a verdict** (B11), so a false OK is worse than none | Reflexion 16.3% false positives C; Olausson inaccurate feedback 32/80 C; Valmeekam C | Is "OK" printed only when a selected test executed the changed lines? Otherwise does it say "KEPT, NOT CHECKED: no test runs these lines"? |
| F4 | **Resisting a challenge**: "are you sure?"-style questions make it change correct work | Huang 75.8 → 38.1 C; FlipFlop 46% flips, −17% C | Does any answer ask the model to reconsider ("is it covered?") without a new fact? Is every heuristic result labelled as a heuristic? |
| F5 | **Knowing what is done** after compaction | Recap +16/+17.5 pts C; Manus todo.md P; Anthropic progress file V | Does every answer start with one line, built from `git diff`, of what is kept, what is current and what is left? Is success stated as a plain word, in the same place every time? |
| F6 | **Profiting from a 3rd retry** of the same thing | 2 rounds = 76–95% of gains C; DDI decay C; Olausson 0.97× vs 1.05× C | After 2 failed edits of a place, does the script move on? Does the next view show fresh code with no trace of the failed text? Do refused and repeated calls stay off the failure count? |
| F7 | **Leaving a loop on its own**, worse with near-greedy decoding | Manus structured variation P; OpenRouter/OpenHands ladders P; Laban temp-0 C | Does a repeated call get an answer that differs from the last one and a different filled NEXT? Does the 3rd repeat move the work on in every step? |
| F8 | **Recovering from harness errors we cannot change** (missing tool: 39.9% recovery) | Loud Failures C; Anthropic V; V10: 34 repeats O | Does the prompt quote each harness error the model has hit, with the exact fixed call? |
| F9 | **Using advice**: facts help, instructions do not | Falsification +15 vs placebo, instructions +3 n.s. C; FeedbackEval verbal is the worst B | Is every verdict a fact (test, value, line) rather than advice? Is each instruction sentence in it at most one line? |

## Not verified or not found
- No head-to-head study of actionable vs non-actionable error **text** with recovery rates. Loud Failures varies the fault, not the wording.
- The Self-Debugging per-format numbers come from the ICLR PDF tables. LDB, the traces paper (2505.04441), Falsification, Debugging Decay's "60–80%" and Zhang et al. are from abstracts only.
- The OpenAI "intern test" is again only in third-party copies. OpenAI's official error-return guidance was not found.
- No controlled evidence on praise or positive messages alone.
- FlipFlop's direction of flips (right→wrong vs wrong→right): the search summaries contradicted each other, so only the 46% and −17% are cited.
